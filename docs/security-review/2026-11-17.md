## High — previously disclosed credentials require rotation

Earlier conversation context contains database credentials, provider secret keys, storage credentials and scheduler/webhook secrets. This is an operational exposure, not a hardcoded-secret finding in the repository. Their current validity and rotation status were not checked. If still valid, possession can permit database access, storage operations, email sending or forged scheduler/webhook requests, depending on the credential.

Action: replace disclosed secrets through each provider, update the corresponding local/hosting configuration, deploy, verify services, and revoke old credentials. Coordinate webhook secret changes with providers. Public Clerk publishable keys, OAuth client IDs and PostHog project tokens are not private credentials. Never copy secret values into this report.

Before: disclosed credential remains active. After: newly issued credential is configured and the disclosed credential is revoked. Do not rotate the integration encryption key casually: existing encrypted Slack tokens need a deliberate re-encryption/reconnection plan.

## Medium — public feedback reads have unbounded work

Locations: `src/server/actions/feedback.ts:45`, `:66`; `src/server/feedback-access.ts:17`.

`readBoard` loads every post, then every matching comment, tag, status event and attachment. Reads have no request rate limit. Guest bootstrapping is limited, but a caller can reuse one existing token indefinitely without consuming that bootstrap limit. An attacker can repeatedly invoke an expensive read, increasing database load and function/bandwidth costs. The effect grows with board size. Mutations also return a full board.

Remediation design (not applied): paginate posts and comments using stable cursors; return only the changed record after mutations; add bounded per-visitor/account and trusted-IP read limits. Do not truncate existing lists silently without implementing pagination in consumers.

```ts
// Before: all matching posts and related comments.
return {items: await readBoard(wid, bid, who)};

// After: proposed API contract, requiring matching UI work.
await enforceReadBudget(wid, who);
return readBoardPage({workspaceId: wid, boardId: bid, actor: who, cursor, limit: 25});
```

## Medium — guest email ownership is not verified

Locations: `src/server/actions/feedback.ts:87`, `src/server/activity.ts:22`, `src/server/chat/service.ts:96`, `src/server/chat/notifications.ts:21`, `:47`.

Guest feedback and chat accept a syntactically valid email without proving mailbox ownership. Subsequent team replies/status updates can send mail to that address; chat reply emails include the team's message. Someone can supply another person's address, cause unwanted mail, and mislead an operator into treating the visitor as that person. This is not a demonstrated account-login bypass. Rate limits and the need for a team reply constrain abuse, but do not establish identity.

Remediation design (not applied): identify guest addresses as unverified in operator UI, verify ownership with an expiring single-use link/code before sending transcript/update notifications, and rate-limit verification per mailbox, visitor and workspace. Reset verification whenever the address changes. Keep anonymous chat available if configured.

```ts
// Before: nonempty guest address is sufficient.
if (event === 'reply' && conv.email) enqueueReplyEmail();

// After: proposed persisted verification state and worker recheck.
if (event === 'reply' && conv.email && conv.emailVerifiedAt) enqueueReplyEmail();
```

## Low — public chat configuration GET lacks a request budget

Location: `src/app/api/chat/[workspaceId]/route.ts:9`.

GET does multiple database lookups and schedules a presence refresh without calling `limitChatRequest`; other chat handlers use that limiter. Slack refreshes are separately leased to one batch per workspace/minute, limiting provider calls, but repeated GETs still perform database work.

Proposed change: accept the Request argument and call `await limitChatRequest(request)` before the public configuration queries, with a polling-appropriate budget. Preserve the presence lease.

## Controls checked

- No matches for the scanned provider-token, database-password or private-key patterns in tracked files or historical added lines across local Git refs. This was a custom pattern scan, not Gitleaks or proof that every possible credential format is absent. Unfetched remote-only branches are outside scope.
- `.env.local` is ignored; only `.env.example` and the server environment module matched tracked environment filenames. Private values were not printed. Server environment parsing is protected by `server-only`.
- The widget uses an iframe, textContent for its label, URL-encoded workspace/board parameters, and origin plus source checks for incoming postMessage events. No transcript or visitor token is sent to the host through those messages. Installing the external widget script still grants that script normal host-page JavaScript privileges; version control, hosting access and release integrity remain important.
- Reviewed team chat/settings/billing/feedback mutations use server-side authentication and workspace roles, not just sidebar visibility. Visitor chat access uses a random 256-bit bearer token hashed in the database and scoped to workspace/conversation. Guest tokens remain browser-readable for persistence, so an XSS on Ent's origin would expose them; they are not Clerk account sessions.
- Slack OAuth uses an encrypted HttpOnly state cookie bound to user/workspace/provider, checks nonce/expiry, and rechecks role at callback. Integration secrets use AES-GCM with workspace/provider context. Slack inbound events validate raw-body HMAC and timestamp; imported replies/status actions match the Slack team, channel/thread and active Ent membership.
- Billing webhooks verify signatures with timestamp tolerance and bounded bodies; application verifies organization, provider state and checkout/workspace bindings, with deduplication. Trial claims are enforced on the server. Focused tests also reject forged prepaid bindings.
- Image inputs are bounded, decoded and re-encoded to WebP. Knowledge crawling is currently blocked by the AI feature flag; the crawler validates public DNS addresses, pins the connection, restricts redirects and has byte/time/page limits.
- Reviewed email templates escape user text and validate link schemes. Unexpected service errors redact provider/ORM payloads. Docs proxy strips application credentials and uses a restricted Mintlify origin. Ordinary app pages restrict framing; `/embed` intentionally allows it.

## Actual signup flow and the repeated name

1. Landing-page signup opens Clerk via `/auth?mode=signup&intent=workspace`. Clerk owns authentication, verification and any configured name/social-login fields. Those dashboard settings were not inspected.
2. Clerk creates the authenticated session, then redirects to `/auth/continue`. Users are already signed in before Ent's workspace onboarding; finishing onboarding does not create a second session.
3. Public-board intent returns to the board/item without workspace setup. Invitations return to acceptance. Existing workspace members go to management unless they have unfinished setup recorded.
4. A new management user with no workspace goes to `/registration`.
5. The current wizard has **two steps**, not the earlier four-step concept: Profile, then Workspace. Profile asks for first and last name plus an optional photo, prefilling from Clerk. It still shows this step even if both names already exist. Saving writes those names back to Clerk and the app's user record.
6. Workspace collects an optional website, workspace name and domain slug. Creation atomically creates the owner membership and a default **Product feedback** board. Registration is marked complete, then the user goes to the dashboard with the welcome-tour parameter. Integrations and invitations are no longer onboarding steps in this component.

Evidence: `src/components/feedback/auth-widget.tsx`, `src/app/auth/continue/page.tsx`, `src/app/registration/page.tsx:24`, `src/components/feedback/registration-wizard.tsx:22-40`, `src/server/actions/registration.ts`, `src/server/services/workspaces.ts:173`.

Recommended UX: if Clerk already supplies a complete first and last name, start at Workspace and leave optional photo/profile editing in Account settings. Otherwise show Profile once. This works for both Clerk-collected names and social-provider names; disabling required name fields in Clerk is a separate dashboard choice. No onboarding behavior was changed during this audit.
